1. Pourquoi --no-verify fonctionne-t-il, et quelle est la seule parade réellement efficace ?
Les hooks Git (pre-commit, commit-msg, pre-push) sont de simples scripts stockés dans .git/hooks/ sur la machine du développeur. Ils ne font pas partie du protocole Git lui-même : ce sont des automatismes locaux, exécutés par le client, avant qu'aucune donnée ne soit envoyée au serveur. Quiconque contrôle sa machine peut les désactiver (--no-verify), les modifier, les supprimer, ou simplement ne jamais les installer (pre-commit install n'est jamais imposé automatiquement au clone). Un garde-fou purement côté client ne peut donc jamais être une garantie — seulement une aide au développeur de bonne volonté.
La seule parade réellement efficace : déplacer le contrôle là où le développeur n'a pas la main — côté serveur. Concrètement : un hook pre-receive sur un serveur Git auto-hébergé (qui peut rejeter un push entier si un secret est détecté dans les commits reçus), ou, sur GitHub/GitLab, des required status checks / règles de protection de branche qui exigent qu'un pipeline CI exécutant gitleaks (ou équivalent) réussisse avant toute fusion, combinés à des fonctionnalités natives de la plateforme comme le push protection pour les secrets. Dans ce cas, --no-verify reste utilisable localement, mais n'a plus aucun effet sur ce que le serveur accepte ou refuse.
2. Le secret purgé était-il, à un moment, présent sur le serveur distant ? Qu'aurait-il fallu faire en premier s'il avait été réel ?
Dans la reproduction de ce TP, l'ensemble des opérations (création du fichier, commit forcé, purge) a été effectué localement, avant tout push — le secret n'a donc, dans cette exécution précise, jamais transité par le serveur distant. Mais la séquence pédagogique du TP place le git push initial avant la création du faux secret ; si le commit contenant la clé avait, lui aussi, été poussé avant la purge, la réponse serait oui — et purger l'historique local ne suffit alors plus.
Ce qu'il aurait fallu faire en premier, si la clé avait été réelle : révoquer/faire tourner (rotate) l'identifiant compromis à la source — ici, désactiver puis supprimer la clé d'accès dans la console IAM AWS — avant même de toucher à l'historique Git. Dès l'instant où un secret réel est poussé sur un serveur distant, il faut le considérer comme compromis de façon définitive : il peut avoir été cloné, forké, mis en cache par la plateforme (recherche, diffs de pull request, journaux CI, alertes de scanning automatique), ou récupéré par un tiers en quelques secondes. Réécrire l'historique avec git filter-repo et forcer le push est une mesure d'hygiène nécessaire ensuite, mais elle n'annule pas une exposition déjà survenue — seule la révocation de la clé elle-même neutralise le risque réel.
3. En quoi la mutabilité des tags Git explique-t-elle l'incident tj-actions/changed-files ?
En mars 2025, l'action GitHub tj-actions/changed-files a été compromise : des attaquants ayant obtenu un accès en écriture au dépôt ont poussé un commit malveillant, puis ont redirigé rétroactivement plusieurs tags de version existants (par exemple v35 à v46) pour qu'ils pointent tous vers ce commit malveillant, sans jamais publier de nouvelle version au sens habituel.
Or, un tag Git n'est — sauf s'il est explicitement signé et vérifié — qu'une simple référence mobile vers un commit, exactement comme une branche : rien n'empêche quiconque possède un accès en écriture de la faire pointer ailleurs a posteriori. Les dizaines de milliers de workflows GitHub Actions qui référençaient l'action via tj-actions/changed-files@v44 (une version « figée » en apparence) ont donc silencieusement exécuté le code malveillant à leur exécution suivante, sans qu'aucune ligne de leur propre configuration n'ait changé. C'est précisément le même principe que celui vu en Exercice 2.2 : une référence non cryptographiquement immuable (un tag, un nom d'auteur déclaratif) ne peut pas servir de preuve d'intégrité. La parade recommandée depuis cet incident est d'épingler les actions tierces sur un hachage de commit immuable plutôt que sur un tag sémantique — un commit SHA ne peut, lui, plus être redirigé après coup.
4. Trois éléments du dépôt relevant de la gestion de configuration au sens ITIL
La gestion de configuration ITIL consiste à identifier, enregistrer, contrôler et vérifier les éléments de configuration (CI) et leurs relations tout au long de leur cycle de vie. Trois éléments de ce dépôt en relèvent directement :
●	Le code d'infrastructure lui-même (fichiers Terraform, à venir dans ce dépôt) : chaque ressource déclarée est un élément de configuration au sens strict — une description versionnée et vérifiable de l'état désiré d'une ressource réelle (VM, réseau, IAM…).
●	L'historique Git lui-même (commits, auteurs, dates, messages Conventional Commits) : il joue le rôle d'un registre d'audit équivalent à une CMDB — pour chaque changement, on sait qui l'a fait, quand, et pourquoi, ce qui est la finalité même du processus ITIL de gestion des configurations.
●	Les fichiers de configuration d'outillage et de contrôle (.pre-commit-config.yaml, Makefile, .gitattributes/.gitignore/.editorconfig) : ce sont eux-mêmes des éléments de configuration versionnés qui définissent une base de référence connue et reproductible (baseline configuration) — garantissant que chaque environnement de développement et chaque exécution CI appliquent exactement les mêmes règles de contrôle.
